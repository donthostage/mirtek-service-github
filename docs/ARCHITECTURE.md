# Архитектура прототипа 0.4

Модульный FastAPI-сервис принимает обращения через независимый от каналов API. Возвраты и жалобы — первые приоритетные сценарии; наличие, расписание, акции и доставка/самовывоз также присутствуют как предварительные направления. Данные явно синтетические. Реальное семантическое качество и KPI не подтверждены.

## Поток обработки

FastAPI → валидация Pydantic → baseline или AITUNNEL SemanticResult → проверка схемы и цитат → контекст и выбор сценария → read-only источник → проверка структуры, области действия и актуальности → шаблонный ответ либо уточнение/handoff.

app/semantic_aitunnel.py — выбранный AITUNNEL-адаптер; semantic_models.py — строгая схема и программное разрешение дат. classifier.py содержит интерфейс и отдельный лексический baseline. Старый aitunnel.py предоставляет общий ограниченный HTTP-вызов и исторический intent-only адаптер для регрессий, но settings.py выбирает семантический вариант.

app/service.py управляет диалогом. pull_flow.py обрабатывает складские остатки, правила, расписание, акции и доставку. source_api.py сам запрашивает отдельный HTTP-источник. contracts/ определяет шлюз, перед которым может стоять нормализатор. contracts/mock_api.py запускает вымышленный источник на отдельном порте. Режим snapshot по-прежнему читает учебные JSON-снимки через sources.py и нужен для старых регрессий.

## Контекст

В памяти одного процесса сохраняются pending_field, известные параметры, исходная тема и вид запроса, счётчик уточнений и исходные слова клиента. Токен непрогнозируемый, TTL 15 минут, предел 1000 записей и 6000 символов накопленного текста. Новая полная тема сбрасывает старые параметры. В HTTP-потоке максимум два уточнения. При нескольких worker-процессах нужно общее хранилище; публичная эксплуатация с таким контекстом не заявляется.

## Границы модели

Модель определяет смысл, но не создаёт факты и не меняет данные. Все новые упоминания подтверждаются фрагментом текущего сообщения. Старые параметры сервер наследует из своего контекста; модель получает только структурированное ожидаемое состояние. Дата вычисляется программно. Правильная цитата ещё не доказывает правильную интерпретацию — для этого нужна оценка выбранной модели на обращениях.

Тексты правил и складские количества возвращает источник. Решение о выплате, одобрение возврата, регистрация жалобы и доставка сотруднику не выполняются. Handoff — признак и пакет для вызывающей системы; handoff_delivered=false. При двух темах обе сохраняются для оператора. При сбое модели нет скрытого перехода на baseline, при сбое HTTP-источника нет подмены старыми локальными остатками.

## Сетевые ограничения

Провайдер — AITUNNEL, выбранный пользователем и разрешённый по уточнению заказчика. Ключи только в серверном окружении. Endpoint источника задаётся сервером, не клиентским текстом; HTTPS обязателен кроме буквального loopback. Перенаправления, системные прокси и повторы отключены. Ответ ограничен 64 КиБ. Общий отменяемый бюджет до 3.5 секунды для модели и до 1 секунды для источника реализован через asyncio.timeout и AsyncClient; медленный поток отменяется и закрывается. Это не доказательство нагрузочного KPI.

## Почему без собственной модели и лишней инфраструктуры

Достаточно небольшой системы вокруг существующей LLM и проверяемых источников. Для двух учебных магазинов снимки подходят. SQL от модели, обучение своей нейросети, микросервисы и автономные агенты не нужны. RAG понадобится, если реальные правила окажутся объёмными и поиск целого документа перестанет работать; PostgreSQL — при согласованной истории, нескольких процессах и требованиях эксплуатации.

## Состояние проверки

Тесты проверяют контракт модели на вручную заданных ответах и поведение источников. Live AITUNNEL не проверен: ключ и модель не настроены. compare_models.py позволяет подготовить ограниченное сравнение без вызовов по умолчанию. Настоящий локальный TCP/HTTP тестируется отдельным smoke. Актуальная проверка комплекта — VERIFICATION.md; непокрытые требования — REQUIREMENTS_AUDIT.md; вопросы заказчику — OPEN_QUESTIONS.md.
