# Возвраты и жалобы

Обновление 0.3: исходящие запросы к отдельному моку источника подключены к основному API сообщений для правил возвратов/жалоб и складских остатков. Подробности — HTTP_PULL.md. Семантическое извлечение параметров пока не реализовано: используется консервативный программный разбор. Ниже сохранён проект поведения; его пометки о неподключённом runtime относятся к предыдущему этапу.

## Решения и статус проекта

Первой итерацией делаем возвраты и жалобы. Пользователь подтвердил разрешение использовать AITUNNEL без дополнительных ограничений со стороны компании и уточнил, что это первые сценарии автоматизации. Компания разрешила моки и предложила нам спроектировать API-контракты. Конкретные правила возврата, сроки, условия рассмотрения жалоб, контакты и реальные интерфейсы ещё не предоставлены.

Ниже описаны поведение и контракты. В версии 0.3 HTTP pull и решения contracts/workflow.py используются основным обработчиком. Тема правила и параметры пока определяются консервативной программной логикой; реальное семантическое понимание нового потока не проверено.

Минимум пять сценариев из PDF сохраняется для итогового проекта. Эта итерация закрывает два приоритетных направления; окончательный набор остальных определяется по обращениям, а не искусственным дроблением возвратов на пять сценариев.

## Как обрабатываем сообщение

1. API получает текст и токен продолжения. Явная просьба сотрудника немедленно ведёт к handoff.
2. AITUNNEL возвращает проверяемый разбор: returns/complaints, вид запроса, явно указанный канал покупки и признаки неопределённости. Упоминания и извлечённые параметры сверяются с исходным текстом. Модель не принимает решения о возврате и не вызывает произвольные URL или SQL.
3. Сервер решает: нужен текст правил, одно полезное уточнение или человек. Одновременно связанные возврат и жалоба сохраняются в пакете оператору; части обращения не теряются.
4. Для общего вопроса сервер читает подходящую версию правил через адаптер только на чтение. Мок сейчас заменяет источник компании.
5. Ответ формируется из подтверждённого фрагмента правил. Результат API: answered, needs_clarification или handoff; плюс причина, источники и время проверки.

Если модель не вернула корректную схему, не уверена, источник недоступен, устарел или правила противоречат друг другу — handoff. При ожидании уточнения не считать обращение решённым. Предлагаемый бюджет — до двух уточнений на диалог, затем handoff; это проектное решение для проверки на примерах.

## Возвраты

Общие вопросы «Как оформить возврат?», «Что нужно подготовить?», «Где посмотреть условия?» разрешено автоматически обрабатывать, если ответ есть в подходящем источнике. Не требуем номер заказа, телефон и ФИО, чтобы показать общую инструкцию.

Если правила зависят от места покупки, а канал неизвестен, спрашиваем только его: «Покупали в магазине, на сайте или на маркетплейсе?» Если правило общее для всех каналов, этот вопрос не нужен. Маркетплейс упоминается как канал покупки; подключение к нему не входит в проект.

«Хочу вернуть покупку», «Одобрите возврат», «Верните деньги», «Мне отказали», «Когда вернут деньги?» и спор о конкретном товаре направляются сотруднику. Можно собрать короткое описание причины, если это действительно нужно по утверждённому процессу, но не задерживать передачу обязательной анкетой. Статус конкретного возврата нельзя проверять по одному номеру заказа без согласованного доступа и проверки права клиента на информацию; такого интерфейса в первой итерации нет.

Сервис не решает самостоятельно, подлежит ли товар возврату, не меняет заказ, не делает выплату и не обещает сумму или срок. Не придумываем правила для ткани на отрез, брака, чека и сроков: нужны тексты компании. Это граница автоматизации, а не утверждение о правовых требованиях к возвратам.

## Жалобы

«Как оставить жалобу?» и «Каков порядок рассмотрения?» — общая инструкция из источника компании. Ответ о канале связи, сроке или порядке допустим только при наличии этого факта в источнике.

«Хочу пожаловаться на сотрудника», «Привезли брак», «Не решили проблему», «Требую компенсацию» — реальная ситуация для человека. Сервис распознаёт тему, сохраняет доступное описание как утверждение клиента и формирует handoff. Вопрос «Что произошло?» полезен, если жалоба не описана; но передать оператору можно и без ответа, особенно если клиент прямо просит человека. Тон ответа спокойный, без оспаривания рассказа клиента и без признания непроверенных обстоятельств от имени компании.

Handoff не означает, что жалоба зарегистрирована или сотрудник уведомлён. Пока нет механизма доставки, возвращаем handoff_delivered=false. Не создаём номер заявки и не обещаем обратный звонок. Клиентский текст прямо сообщает, что необходим сотрудник, а автоматическая отправка в прототипе отсутствует.

## Два разных API

**Клиентский API нашего сервиса:** POST /api/v1/messages. Принимает сообщение, возвращает ответ, уточнение или признак оператора. Этот адрес уже есть; новая реализация расширит его без отдельного канала интеграции.

**Предлагаемый API источника:** POST /source/v1/policies/resolve. Наш сервис отправляет структурированный вопрос, например сценарий returns, тему steps и канал store; получает правило, его область применения, версию и актуальность. Сейчас его роль выполняет мок. Это наш проект интерфейса, а не обнаруженный endpoint Миртека и не обязательство компании его реализовать.

Компании можно показать контракты и пример обмена. Если у неё уже есть иной API или только выгрузка документов, адаптер преобразует их в тот же внутренний контракт. В этой итерации достаточно одного read-only метода правил; интерфейсы заказов, выплат, регистрации жалоб и внешних каналов не требуются.

## Разбор LLM

Проект схемы ParseResult: scenarios, request_kind, topic, purchase_channel, uncertain. request_kind разделяет policy_question, individual_case, operator_request, unsupported. topic — steps, documents, conditions, complaint_procedure, complaint_review или null. Значения из разрешённого списка, неизвестные поля запрещены. Схема не содержит суммы, срока возврата, решения об одобрении и свободного ответа клиенту.

Сама корректность JSON не доказывает правильность понимания. Два класса критических ошибок для тестов: просьбу вернуть деньги принять за общий вопрос и жалобу на товар принять за вопрос о порядке подачи жалобы. Нужно сравнение с эталонами на реальных обезличенных обращениях. Для продолжения передаём модели ограниченный контекст ожидаемого вопроса, а не только сценарий: это предотвращает потерю смысла ответа «в магазине».

Серверный контекст хранит сценарий, pending_field, уже известные структурированные поля, счётчик уточнений и срок жизни. Клиент не может подставить свои scenario/channel/source_id через токен. При смене темы сбрасываем несовместимые поля. Имеющийся TTL 15 минут и предел 1000 записей подходят для локальной версии; при нескольких процессах потребуется общее хранилище.

## Источники и моки

Контракт PolicyQuery передаёт только сценарий, тему и канал; исходный текст клиента и личные сведения источнику правил не нужны. PolicyResult различает found, needs_context, not_found, unavailable. При found правило обязано совпадать со сценарием, темой и каналом запроса; нельзя взять случайный близкий текст.

PolicyDocument содержит id, version, as_of, valid_until, scenario, topic, channel и text. approval_state имеет значения synthetic_demo и company_approved. Мок всегда synthetic_demo и не может использоваться в реальном режиме. Для company_approved дополнительно нужны данные о том, кто и когда подтвердил правило; даты должны быть согласованы. Ошибка чтения, отсутствующее правило и просроченная версия не превращаются в пустую общую инструкцию.

В моках нет выдуманных правовых норм, сроков и адресов. Тексты явно учебные. Приёмка реального источника включает проверку актуальности, области действия, конфликтующих версий и ответственности за обновление.

## Передача человеку

Внутренний HandoffPayload содержит scenarios, reason_code, request_id, customer_text и known_fields. customer_text — исходное утверждение клиента, не подтверждённый факт. Номер заказа, контакт и иные сведения не собираем про запас. Свободное LLM-резюме не заменяет оригинал, не добавляет событие, обещание или срок.

Этот пакет предназначен для вызывающей системы. Возврат его в API ещё не доставляет сообщение оператору. В первом прототипе handoff_delivered всегда false; отдельный механизм доставки требует согласованного объёма и подтверждения внешней системы. Сырые диалоги и ключи не пишем в логи. Разрешение пользоваться AITUNNEL не означает, что нужно передавать ему все данные компании.

## Примеры ожидаемого поведения

1. «Как оформить возврат?» → если есть общая инструкция, answered с источником. Если инструкции различаются по каналам, needs_clarification с вопросом о месте покупки.
2. «В магазине» после этого уточнения → инструкция для магазина и answered. Если такого правила нет — handoff.
3. «Хочу вернуть отрезанную ткань» → individual_case, handoff. Не угадывать допустимость возврата.
4. «Какие документы нужны для возврата?» → текст подходящего правила либо handoff, если текста нет. Не выдумывать обязательность чека.
5. «Как оставить жалобу?» → утверждённый порядок, answered.
6. «Мне нагрубили, хочу пожаловаться» → complaints, handoff с исходным описанием. Не писать «жалоба зарегистрирована».
7. «Привезли брак, хочу возврат и жалобу» → returns и complaints в одном handoff, без потери второй темы.
8. «Где мои деньги по возврату?» → handoff: статуса возврата у сервиса нет.
9. «Позовите человека» → немедленный handoff, без анкеты и платного вызова модели.
10. Неизвестный вопрос, неопределённый разбор, сбой модели, неподходящая/старая инструкция → handoff с конкретной причиной.

## Реализация по порядку

1. Выполнено: схемы, примеры и исполнимая логика решений.
2. Выполнено частично: добавлен complaints и общий вопрос о жалобе может получать инструкцию. Конкретные случаи и брак безопасно направляются оператору; семантический разбор видов запроса предстоит проверить.
3. Выполнено: решения, ограниченный контекст и HTTP-адаптер правил на отдельном моке подключены к app/service.py.
4. Дополнить AITUNNEL-промпт и проверку параметров, затем проверить несколько живых синтетических диалогов после настройки ключа и модели.
5. Показать Миртеку примеры PolicyQuery/PolicyResult; получить реальные тексты и уточнить допустимые автоматические ответы.
6. Проверить новый поток на независимых обращениях и затем расширять остальные сценарии. Автоматическую отправку оператору и реальные изменения заказов не считать реализованными.
